# lina.co.kr 출시 전 보안 점검 — 공개 영역 1차 결과

점검일: 2026-10-28 (Asia/Seoul)  
대상: `https://www.lina.co.kr`  
상태: **공개 응답 점검 및 로컬 재현 완료. 소스 검토·원본 수정·인증 기능 검증은 미완료. 출시 가능 판정을 내릴 수 없음.**

추가 검증: [추가 보고서](report-additional.ko.md)에서 공개 번들의 토큰 저장 코드(F-05), URL 쿼리 저장(F-06), HTML sink, HTTPS 인증서 검증 결과를 보완했습니다. 아래 본문은 최초 점검 범위의 기록이며, 실제 로그인·계정 접근·운영 수정은 추가 검증에서도 수행하지 않았습니다.

3차 검토: [외부 침입 가능성 검토](intrusion-review.ko.md)에서 API 오류 메시지의 HTML 전달 경로(F-07), 갱신 토큰 덮어쓰기(F-08), Axios XSRF 동작(F-09)을 추가 확인했습니다. 서버 침입·계정 탈취는 입증하지 않았으며 안전 판정도 내리지 않았습니다.

## 범위와 한계

사용자가 이 도메인 및 제공 소스에 대한 점검을 허가했습니다. 시작 시 `C:\codex_pen_test`에는 소스코드·설정·저장소·AGENTS.md가 없었습니다. 로컬 코드 경로/저장소 URL과 환경 구분을 요청했으며, 본 보고서는 그 자료 없이 수행 가능한 범위입니다. 이후 생성된 `audit/`는 점검 산출물입니다.

대상 환경은 확정되지 않았습니다. 공개 HTML에 `LINA_SERVER_TYPE = 'prd'`, `VUE_APP_NODE_MODE: "production"` 표시가 있어 운영 환경으로 취급했습니다. 이 표시는 인프라 환경을 독립적으로 입증하지 않습니다.

정상적인 GET으로 홈페이지, HTML에 등장한 `/login`, `/company` 및 직접 참조된 JS 5개를 조회했습니다. HTTP 홈페이지는 HTTPS 전환 확인용입니다. 자동 크롤링·경로 대입·디렉터리 탐색·취약점 스캐너·공격 문자열 전송·폼 제출은 하지 않았습니다. 별도 API/하위 도메인/내부 주소/외부 분석 서비스에는 접속하지 않았습니다. 로그인, 다른 사용자 계정 접근, 데이터 변경, 주문·결제, 부하 테스트도 하지 않았습니다.

브라우저에서 앱 JS를 실행하거나 화면을 조작하지 않았습니다. 서버가 반환한 HTML/JS만 검토했으므로 실제 DOM, 실행 후 라이브러리 버전, 로그인 화면 동작, 민감 기능의 프레임 삽입 및 XSS 가능성은 미확인입니다.

## F-01 — 구버전 jQuery 이중 참조

**근거**

- R01(홈) 및 R03(`/login`)의 HTML은 `/lib/jquery-3.7.1.js`를 먼저 참조하고, 그 뒤 `/lib/jquery/1.12.4/jquery.min.js`를 동기 `<script>`로 참조합니다.
- R05 응답 첫머리: `jQuery JavaScript Library v3.7.1`.
- R06 응답 첫머리: `jQuery v1.12.4`.
- 단순 파일명 추측이 아니라 실제 제공 파일의 버전 주석까지 확인했습니다. 배너만으로 모든 코드가 공식 원본과 동일함을 보증하지는 않습니다. 별도 보안 패치를 백포트했는지는 소스/배포 이력 부재로 미확인입니다.
- jQuery 공식 보안 권고의 CVE-2020-11022 영향 범위는 `>=1.2 <3.5.0`, CVE-2020-11023은 `>=1.0.3 <3.5.0`입니다. 1.12.4는 두 범위에 포함됩니다. [공식 권고 11022](https://github.com/jquery/jquery/security/advisories/GHSA-gxr4-xjj5-5px2), [공식 권고 11023](https://github.com/jquery/jquery/security/advisories/GHSA-jpcq-cgw6-v4j6)

**영향**

일반적인 브라우저 로드 동작에서는 뒤에 실행되는 jQuery가 전역 `$`/`jQuery`를 덮어쓸 수 있습니다. 후속 스크립트의 `noConflict` 등은 모두 검토하지 않았으므로 최종 전역 버전은 미확인입니다. 이들 CVE는 신뢰할 수 없는 HTML이 `.html()`, `.append()` 등의 DOM 조작 함수로 전달되는 조건에서 문제가 됩니다. 해당 데이터 흐름은 확인하지 않았고, 이 사이트에서 XSS가 가능하다고 확정하지 않습니다.

**수정 방법**

1. 실제 HTML 템플릿, Nuxt head 설정, CMS 삽입 코드에서 1.12.4 참조를 제거하고 단일 버전만 로드합니다. 이미 있는 3.7.1은 위 두 권고의 취약 범위 밖이지만, 이것이 현재 지원 상태나 전체 의존성 안전성을 보증하지는 않습니다.
2. 호환성과 보안 지원을 확인한 버전으로 정리하고 잠금 파일/SBOM으로 고정합니다. 레거시 플러그인 때문에 구버전을 전역으로 재삽입하지 않도록 합니다.
3. 사용자·CMS 콘텐츠를 출력하는 DOM 경로를 검토하고 텍스트 출력에는 `textContent` 또는 프레임워크의 기본 이스케이프를 사용합니다.

**검증 결과와 남은 일**

- 확인: R01/R03 스크립트 참조, R05/R06 파일 버전. 수집 응답 검사에서 구버전 참조 조건 2건 실패.
- 미확인: 브라우저의 최종 `jQuery.fn.jquery`, 공격자 입력에서 DOM까지의 경로, 레거시 플러그인 호환성.
- 수정 예시: `fixes/nuxt.config.example.js` 주석의 템플릿 정리 지침. 원본 파일이 없어 실제 제거 패치는 작성·적용하지 못했습니다.
- 수정 후: 테스트 환경의 네트워크 목록에서 중복 로드가 없는지 확인하고 인증·검색·팝업·전자서명 등 관련 플러그인 회귀 검사를 수행해야 합니다.

## F-02 — 프레임 삽입 제한과 스크립트 정책 부재

**근거**

R01(홈, 200), R03(`/login`, 200), R04(`/company`, 404)의 헤더에는 `Content-Security-Policy`, `Content-Security-Policy-Report-Only`, `X-Frame-Options`가 없습니다. 수집 HTML에도 CSP meta 정책은 보이지 않습니다. `frame-ancestors`는 HTML meta로 적용할 수 없고 HTTP 응답 헤더가 필요합니다. [MDN frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)

**영향**

관측한 응답에는 다른 사이트의 프레임 삽입을 브라우저에 제한시키는 헤더가 없습니다. 다른 보호 수단이 없다면 화면을 다른 사이트에 삽입해 클릭을 유도할 수 있습니다. 민감 동작이 실제로 가능한지, 쿠키 정책·추가 인증·프레임 감지 코드가 어떻게 작동하는지는 확인하지 않았습니다. 따라서 클릭재킹 성공으로 보고하지 않습니다.

스크립트 실행 출처를 제한하는 CSP도 관측되지 않았습니다. 이는 XSS에 대한 추가 방어층 부재이며, CSP가 없다는 사실만으로 XSS 취약점이 입증되지는 않습니다.

**수정 방법**

- 동일 출처 프레임만 필요하다면 `Content-Security-Policy: frame-ancestors 'self'`와 `X-Frame-Options: SAMEORIGIN`을 적용합니다. 프레임이 전혀 필요 없다면 `'none'`/`DENY`를 선택합니다.
- 제휴 사이트에서 프레임 삽입이 필요한 경우 정확한 HTTPS origin을 CSP에 허용하고, 충돌하는 SAMEORIGIN 정책은 재검토합니다. 무조건 `*`를 사용하지 않습니다.
- CDN·WAF·프록시·앱 중 최종 응답을 관리하는 계층에서 HTML 정상/오류 응답에 일관되게 적용합니다. 서로 다른 계층의 CSP를 덮어쓰거나 충돌시키지 않도록 확인합니다.
- 전체 스크립트 CSP는 기존 인라인 코드와 외부 분석·인증 연동을 파악한 뒤 테스트 환경의 Report-Only 정책으로 호환성을 확인하고 nonce/hash 기반으로 강화합니다. 아래 참고 미들웨어는 **프레임 제한만** 설정하며 전체 XSS 방어 정책은 아닙니다.

**검증 결과와 남은 일**

- 확인: 홈·`/login`의 프레임 제한 응답 검사 2건 실패.
- 참고 수정: `fixes/security-headers.cjs`.
- 로컬 루프백 HTTP 서버에서 200(`/`, `/login`) 및 404(`/missing`) 응답에 프레임 제한·nosniff 헤더가 붙고, 기존 CSP가 있으면 이를 보존하는 것을 검증했습니다.
- 미확인: 실제 CDN을 통과한 수정 응답, 정상 인증·전자서명·제휴 iframe 호환성, 테스트 환경에서 허용/비허용 origin의 브라우저 차단 결과.
- 실제 애플리케이션이나 운영 설정에는 적용하지 않았습니다.

## F-03 — 자체 HTML 방어 함수의 부정확한 동작

**근거**

R01 HTML 인라인 스크립트에 `escapeHtml(value)`와 `excapeHtmlOrReturn(value)`가 정의되어 있습니다. 두 함수만 분리해 네트워크 없이 로컬에서 실행했습니다.

| 입력 / 호출 | 실제 반환값 | 의미 |
|---|---|---|
| `excapeHtmlOrReturn('<b>audit</b>')` | `<b>audit</b>` | 블랙리스트에 걸리지 않는 HTML은 그대로 통과 |
| `excapeHtmlOrReturn('<b onclick="void 0">audit</b>')` | 입력과 동일 | 목록에 없는 이벤트 속성도 통과. 이벤트 자체는 실행하지 않음 |
| `escapeHtml('"')` | `&qout;` | 올바른 `&quot;`가 아닌 오타 |
| `escapeHtml('<')` | `&amp;lt;` | 치환 순서로 새로 생성한 엔티티까지 이중 인코딩 |

**영향과 한계**

블랙리스트 반환값을 HTML 정화 결과로 신뢰해 `v-html`, `innerHTML`, jQuery `.html()` 등에 넣는다면 임의 마크업이 남을 수 있습니다. 반환값이 기본 이스케이프되는 텍스트로만 출력된다면 같은 영향이 없을 수 있습니다. 호출 위치와 입력 출처를 확인하지 못했으므로 반사형/저장형/DOM XSS로 분류하거나 실제 악용 가능성을 확정하지 않습니다. 엔티티 오타와 이중 인코딩 자체도 XSS 성공 증거가 아닙니다.

**수정 방법**

- 텍스트 출력은 Vue `{{ value }}`/`v-text` 또는 DOM `textContent`를 우선 사용합니다. 기본 이스케이프와 수동 인코딩을 중복 적용하지 않습니다.
- 텍스트를 수동 HTML 문자열로 만들어야 하는 제한된 경우 `fixes/safe-html.mjs`처럼 메타문자를 한 번의 치환으로 인코딩합니다. `excapeHtmlOrReturn`의 조건부 우회 경로를 제거해야 합니다.
- 이 참고 인코더는 HTML 텍스트 및 따옴표로 감싼 일반 텍스트 속성용입니다. URL·JS·CSS·이벤트 속성이나 무따옴표 속성에 적용하는 범용 보안 함수가 아닙니다. URL은 허용 프로토콜/출처 검증이 별도로 필요합니다.
- 리치 HTML이 필요하면 유지 관리되는 HTML 정화기를 올바르게 설정하고 실제 sink에서 검증합니다. 입력 검증과 출력 문맥별 처리는 서버에서도 별도로 수행합니다. [OWASP 출력 인코딩·안전한 sink 지침](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)

**검증 결과와 남은 일**

- `reproduce.mjs`: 기존 함수 동작 4건 재현. 결과는 `evidence/local-reproduction.json`.
- 수정 참고 코드: 메타문자, 미등록 이벤트 마크업, 엔티티 텍스트, 한국어/빈 값에 대한 로컬 회귀 검사 통과.
- 원래 함수의 전체 호출 위치, 사용자/CMS 입력 도달 여부, 브라우저 DOM 결과, 실제 앱에 수정 함수가 통합됐는지는 미확인입니다.

## F-04 — 공개 상태에 내부 서비스 주소 직렬화

**근거**

R01/R03의 `window.__NUXT__` 설정에 다음 키가 포함됩니다.

```text
VUE_APP_PRIVATE_COMMON_API_DOMAIN
PRIVATE_DOMAINS.common
http://ldc-api-common.service-ldc.svc:8080
```

**영향**

비로그인 사용자에게 내부 서비스 이름·네임스페이스로 보이는 문자열·포트가 공개됩니다. 내부 주소로 접근하거나 DNS를 조회하지 않았고, 내부망 접근·SSRF·인증 우회가 가능하다고 주장하지 않습니다. 현재 확인한 내용은 내부 구성 정보 노출입니다.

공개 HTML에는 프런트엔드용 client ID/JavaScript key로 보이는 설정도 있습니다. 이름이나 노출 자체만으로 비밀키 유출이라고 판정하지 않았습니다. 공급자별 허용 도메인·사용 범위와 실제 키 유형은 설정 검토가 필요합니다. 키를 이용한 API 호출은 하지 않았습니다.

**수정 방법**

- 브라우저에 필요한 설정만 허용 목록으로 공개합니다. 내부 주소는 서버 전용 설정으로 분리하고 Vuex/SSR 초기 상태·HTML·클라이언트 번들에도 직렬화하지 않습니다.
- 실제 Nuxt 2 프로젝트라면 `publicRuntimeConfig`와 서버 전용 `privateRuntimeConfig` 분리를 확인할 수 있습니다. 정확한 버전과 지원 상태는 잠금 파일로 확인해야 합니다. [Nuxt 공식 runtime config 문서](https://nuxt.com/docs/2.x/api/configuration/configuration-runtime-config)
- `fixes/nuxt.config.example.js`는 구조 참고용이며, 실제 설정 전체를 대체하는 파일이 아닙니다. 서버 호출부와 `$config` 사용 위치를 확인해 수정해야 합니다.

**검증 결과와 남은 일**

- 수집 HTML의 내부 설정 노출 조건 2건 실패.
- 실제 구성 수정과 서버 호출 회귀 검사는 소스 부재로 수행하지 못했습니다.
- 수정 후 SSR HTML 및 브라우저 번들에서 내부 설정/주소가 빠졌는지 확인하고 서버 내부 호출이 계속 정상 동작하는지 테스트해야 합니다.

## 세션·쿠키 관찰 사항 — 취약점 확정 아님

HTTPS 공개 응답에서 다음 쿠키 속성을 관측했습니다. 값은 수집 시 마스킹했습니다.

| 이름 | 관측 속성 | 해석 |
|---|---|---|
| `AWSALB` | `Expires`, `Path=/`; Secure/HttpOnly/SameSite 없음 | AWS 문서상 로드밸런서 고정 라우팅 쿠키. 인증 세션으로 단정하지 않음 |
| `AWSALBCORS` | `Expires`, `Path=/`, `SameSite=None`, `Secure`; HttpOnly 없음 | AWS가 설명한 CORS 고정 라우팅 쿠키 동작과 일치 |
| `TS011388cf` | `Path=/`; Secure/HttpOnly/SameSite 없음 | 발급 주체와 용도 미확인. 인프라 담당자 확인 필요 |

이 결과를 인증 세션 탈취나 CSRF 취약점으로 보고하지 않았습니다. `AWSALB`류는 앱 인증 세션 쿠키와 구분해야 하고, 실제 수정 가능 속성도 발급 계층별로 확인해야 합니다. [AWS 고정 세션 문서](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-target-group-attributes.html#sticky-sessions)

실제 인증 쿠키/토큰은 로그인하지 않아 관측하지 못했습니다. 로그인 시 세션 ID 재발급, 로그아웃/만료 후 서버 거부, refresh token 회전, idle/absolute timeout, Secure·HttpOnly·적절한 SameSite, CSRF 보호는 모두 미확인입니다.

## 정상 확인된 공개 응답

- HTTP 홈: 301, `Location: https://www.lina.co.kr/`.
- HTTPS 홈 및 `/login`: 200.
- 관측 HTTPS HTML: `Strict-Transport-Security: max-age=31536000 ; includeSubDomains; preload`, `X-Content-Type-Options: nosniff`, `Cache-Control: no-cache, no-store, must-revalidate`.
- HSTS 헤더의 `preload` 문구는 실제 브라우저 preload 목록 등재를 입증하지 않습니다.
- HTTPS 조회는 TLS 검증을 끄지 않고 성공했습니다. 전체 TLS 버전/암호군/인증서 설정 점검은 수행하지 않았습니다.
- `/company`는 공개 초기 상태의 메뉴 링크에 등장하지만 GET에서는 404였습니다. 실제 브라우저 라우팅을 확인하지 않았으므로 취약점으로 분류하지 않았습니다. 출시 시 메뉴 목적지 정상 동작을 확인할 필요가 있습니다.

## 검증 산출물과 결과

`check-snapshot.mjs`의 실패는 현재 저장된 서비스 응답에 문제가 남아 있다는 의미입니다. 수정 참고 코드 테스트가 통과해도 현재 서비스가 수정되지는 않습니다. 이 검사는 보안 전체를 평가하거나 출시를 승인하는 도구가 아닙니다.

재실행 방법은 [README.md](README.md)에 있습니다. `collect-public.mjs`를 제외한 재현·검사는 운영 요청을 하지 않습니다.

운영 설정에 변경이 필요한 항목은 F-01~F-04에 정리했습니다. 지금은 모두 로컬 참고 코드/지침으로만 준비했습니다. 실제 소스를 받으면 해당 구조에 맞는 패치와 회귀 테스트를 작성하고, 운영 적용 전 영향 범위를 알려야 합니다.
