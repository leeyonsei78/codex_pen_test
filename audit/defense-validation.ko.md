# 권한 탈취·API 남용 방어를 검증하는 방법

작성일: 2026-10-28 KST  
현재 상태: **검증 절차와 합격 기준 수립. 라이나 실제 서버의 아래 통제는 아직 검증하지 못함.**

## 검증할 질문

정상 계정의 정상 요청이 성공하는지만 확인해서는 권한 우회나 API 남용 방어를 검증할 수 없습니다. 다음 세 가지를 나눠 확인해야 합니다.

1. **권한 획득을 막는가:** 잘못되거나 만료된 인증정보, 일반 계정의 관리 기능 요청, 다른 테스트 계정 소유 객체 요청을 서버가 거부하는가.
2. **일부 권한이 이미 탈취됐어도 피해가 제한되는가:** 유효한 테스트 토큰으로도 권한 밖 데이터·민감 기능·대량 반출이 제한되는가. 앱 서버 서비스 계정 탈취까지 가정하면 DB·내부망 접근 범위도 제한되는가.
3. **반복·동시·장기 호출을 막고 탐지하는가:** 요청 수뿐 아니라 계정별 누적 데이터량·업무 비용·동시 작업 수를 제한하고, 경보와 세션 회수가 작동하는가.

유효한 bearer token을 가진 요청은 서명 검사만으로 실제 사용자와 탈취자를 구별하기 어려울 수 있습니다. 로그인 시 MFA를 통과했더라도 이미 발급된 토큰의 탈취 문제가 자동으로 해결되지는 않습니다. 토큰의 권한·대상 제한, 재사용 방어, 민감 행위의 추가 확인 및 회수 정책을 함께 검증해야 합니다. [IETF OAuth 보안 권고](https://www.rfc-editor.org/rfc/rfc9700.html)

## 준비: 테스트 대상과 정답을 먼저 고정

- 운영과 분리된 테스트 배포를 사용합니다. 인증·인가 미들웨어, 프록시/게이트웨이, 호출 제한 저장소의 구성은 운영과의 차이를 기록합니다.
- 사용자 A/B, 제한된 운영자, 관리자 역할의 **전용 테스트 계정**을 준비합니다. 실제 타인 계정을 사용하지 않습니다.
- A 소유 합성 객체 A1, B 소유 합성 객체 B1, 관리자용 합성 객체를 준비합니다. 각 응답의 식별용 마커로 잘못된 데이터 반환을 확인합니다.
- SMS·메일·결제·대외기관 연동은 모의 처리합니다. 변경 기능 검증은 격리 DB/복구 가능한 합성 데이터로 수행하며 실제 주문·지급·삭제는 하지 않습니다.
- 실제 API 명세를 기준으로 `주체 × 기능 × 객체 × HTTP 메서드 × 데이터 필드`의 허용 표를 작성합니다. 프런트 메뉴가 숨겨졌는지 대신 API 서버의 응답을 직접 검사합니다.
- 각 API의 응답/페이지 크기, 계정·기능·동시 작업 한도, 세션 폐기 기한, 경보 기한을 정합니다. 정답이 없으면 통과/실패도 판정할 수 없습니다.

예시 정답표이며 실제 경로와 권한 모델은 아직 제공되지 않았습니다.

| 주체 | A1 조회 | B1 조회 | 관리 기능 | 대량 내보내기 |
|---|---|---|---|---|
| 비로그인 | 거부 | 거부 | 거부 | 거부 |
| 사용자 A | 허용 | 거부 | 거부 | 명시적으로 허용된 범위만 |
| 사용자 B | 거부 | 허용 | 거부 | 명시적으로 허용된 범위만 |
| 제한된 운영자 | 업무에 명시된 범위만 | 업무에 명시된 범위만 | 일부만 | 별도 권한 필요 |
| 관리자 | 정의된 권한대로 | 정의된 권한대로 | 정의된 권한대로 | 재인증·추가 승인·한도 정책대로 |

정상 허용 요청도 함께 성공해야 합니다. 모든 요청을 차단한 시스템을 안전하다고 오판하지 않도록 합니다.

## 1. 인증·권한 검증: 서버에 거부되어야 할 요청

아래를 승인된 테스트 환경에서 실제 API에 대해 실행합니다. 요청 주소나 객체 ID를 대량 추측하지 않고 미리 만든 A1/B1만 사용합니다.

| ID | 검증 시나리오 | 합격 기준 |
|---|---|---|
| AUTH-01 | 토큰 없음/잘못된 서명/만료 토큰으로 보호된 조회 | 서버 거부. 보호 데이터·DB 변경·외부 부작용 없음 |
| AUTH-02 | 다른 발급자·대상(audience)·토큰 용도를 가진 테스트 토큰 | 해당 API에서 거부. 단순한 서명 유효성만으로 통과시키지 않음 |
| AUTHZ-01 | A 토큰으로 B1의 상세·첨부·내보내기 조회 | 서버 거부. 본문·첨부·메타데이터에 B1의 비공개 값이 없어야 함 |
| AUTHZ-02 | 일반 A 계정으로 관리자/운영자 기능 직접 요청 | 기능별 역할 검사로 거부. URL 이름이나 UI 표시 여부에 의존하지 않음 |
| AUTHZ-03 | 클라이언트가 보낸 사용자/소유자/역할 값을 변경한 합성 요청 | 서버가 신뢰된 인증 주체와 정책으로 판단. 권한 필드 변경이나 다른 소유자 조회가 없어야 함 |
| AUTHZ-04 | 권한이 낮아진 테스트 계정의 기존 세션으로 재요청 | 정해진 권한 변경 반영 기한 안에 민감 기능 거부 |
| AUTHZ-05 | 상세 화면 외 목록·검색·첨부·내보내기·작업 결과 조회 | 모든 데이터 경로에서 같은 소유권/역할 정책 적용 |

일반적으로 미인증은 401, 권한 부족은 403 또는 존재 은폐용 404를 사용할 수 있으나, **상태 코드만으로 통과 판정하지 않습니다.** 오류 본문에 데이터가 함께 오는지, 이미 작업/메일/DB 쓰기가 수행됐는지까지 확인해야 합니다.

근거: [OWASP 객체별 권한](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/), [기능별 권한](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization/).

## 2. 침해를 가정한 검증: 유효한 권한을 가진 공격자

실제 계정을 탈취하지 않고 전용 계정의 토큰을 테스트 도구에 지급해 그 이후의 통제를 확인합니다.

| ID | 검증 시나리오 | 합격 기준 |
|---|---|---|
| SESSION-01 | 유효한 A 토큰으로 정상 조회와 B1/관리 기능 조회를 함께 검사 | 정상 A1 조회만 허용. 로그인 성공이 전체 데이터 접근 권한으로 확대되지 않음 |
| SESSION-02 | 로그아웃/관리자 회수 후 기존 access/refresh token 재사용 | 서버 정책의 폐기 기한 안에 거부. 즉시 차단이 필요한 기능은 서버가 회수 상태를 확인 |
| SESSION-03 | 새 refresh token 발급 후 이전 refresh token 재사용 | 회전 계약에 따라 이전 값 거부·재사용 대응. 단말/탭 동시 갱신 정상 동작도 확인 |
| SESSION-04 | 유효한 일반 세션으로 민감 조회/권한 변경/대량 내보내기 시도 | 별도 권한·재인증·추가 승인 등 해당 업무 정책이 서버에서 적용 |
| BLAST-01 | 테스트 서비스 계정으로 불필요한 DB·다른 서비스·파일 저장소 접근 | 최소권한·네트워크 경계에서 거부. 필요한 정상 접근은 성공 |

관리자에게 원래 전체 데이터 반출 권한이 있다면, 그 관리자 권한을 탈취한 공격자도 같은 기능을 사용할 수 있습니다. 이 경우 별도 반출 권한, 권한 분리, 단기 승인, 데이터 마스킹, 반출량 제한과 독립 관제가 필요한지 설계에서 결정해야 합니다.

앱 서버 권한까지 탈취한 상황에서는 웹 API의 호출 제한을 거치지 않고 데이터 저장소에 접근하려 할 수 있습니다. 서비스 계정 권한, DB/내부망 분리, 외부 반출 경로, 별도 보호된 감사 기록을 함께 검증해야 합니다. 서버 관리자 권한으로 그 서버 자체의 통제를 변경할 수 있는 상황까지 단일 웹 방어로 보증할 수는 없습니다. BLAST-01은 격리된 인프라/데이터 사본에서 승인된 계정으로 수행합니다.

## 3. API 다량 호출 방어: 소량으로 정책을 검증

처음부터 운영에 많은 트래픽을 보내지 않습니다. 먼저 로컬 테스트에서 가상 시계로 정책 경계값을 검사하고, 테스트 배포에서는 **전용 계정의 한도만 낮춰** 소량 요청으로 실제 경로가 제한되는지 확인합니다.

예시: 별도의 테스트 계정 정책을 `분당 5회`로 정한 경우, 고정 윈도우의 충분히 이른 시점에 단일 연결 흐름으로 6~7회만 요청합니다. 이는 라이나 운영 한도 제안이 아니라 테스트 예시입니다. 실제 윈도우·토큰 버킷 등 사용 알고리즘에 맞춰 기대 허용량을 계산해야 합니다.

| ID | 검증 시나리오 | 합격 기준 |
|---|---|---|
| LIMIT-01 | N회까지와 N+1회 요청 | 정책 경계에서 429 등 정의된 거부. 초과 응답에 데이터 없음. 비싼 DB/외부 작업 실행 전에 제한 |
| LIMIT-02 | 같은 계정의 새 토큰·다른 세션·다른 테스트 클라이언트 | 계정 누적 한도가 요구되는 기능에서 한도가 초기화되지 않음 |
| LIMIT-03 | 여러 앱 인스턴스에 같은 계정 요청을 분배하고 소량 동시 요청 | 공유 저장소의 원자적 제한으로 전체 합산 한도 준수. 프로세스별로 한도가 늘지 않음 |
| LIMIT-04 | 테스트 프록시의 다른 주소 및 신뢰하지 않는 전달 헤더 입력 | IP만 바꿔도 계정/기능 제한이 사라지지 않음. 신뢰할 프록시 범위대로 주소 판단 |
| LIMIT-05 | 작은 합성 목록의 페이지 크기·배치 개수·누적 조회량·다운로드량 경계 | 요청 하나의 최대량과 계정/기능별 누적량·작업 수가 정책대로 제한 |
| LIMIT-06 | 낮은 속도로 오랫동안 페이지/기능을 나눠 호출하는 합성 시나리오 | 초당 요청 제한 아래에서도 정해진 누적 데이터량/업무량을 넘어서는 반출 억제·탐지 |
| LIMIT-07 | 한도 회복, 정상 계정 동작, 제한 저장소 오류 | 회복 시점이 정책과 일치. 다른 정상 계정에 불필요한 장애 없음. 저장소 오류 시 위험 기능의 사전 정의된 동작 준수 |

IP 기준만 사용하면 같은 계정의 분산 호출을 놓칠 수 있고, 토큰 문자열만 기준으로 삼으면 토큰 갱신 때 한도가 초기화될 수 있습니다. 반대로 계정 한도만으로는 비로그인 고비용 요청을 제어하지 못할 수 있습니다. **IP/계정/업무/전체 자원에 필요한 제한을 조합**하고 각각의 경계값을 확인합니다.

또한 1초에 몇 번인지만 제한하면 느린 대량 추출을 막지 못할 수 있습니다. 페이지당 레코드 수, 누적 레코드·바이트 수, 동시 작업, 내보내기 권한, 외부 서비스 호출 비용도 검증 대상입니다. 단일 배치 요청이 여러 작업을 수행한다면 실제 작업 단위로 계산해야 합니다. [OWASP 자원 소비 제한](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/), [민감 업무 자동화 남용](https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/).

소량 검사는 정책의 동작을 확인합니다. 실제 처리 한계·가용성은 별도의 격리된 성능 시험에서 총량·동시성·중단 기준을 정해 측정합니다. 이번에는 운영/테스트 어느 API에도 다량 호출을 실행하지 않았습니다.

## 4. 차단 이후의 결과까지 검증

| ID | 검증 시나리오 | 합격 기준 |
|---|---|---|
| OBSERVE-01 | 위 권한 거부/토큰 재사용/호출 초과를 합성 이벤트로 발생 | 요청 ID·정책·주체·행위·거부 이유를 추적할 수 있고, 정해진 기한 안에 테스트 경보 확인 |
| CONTAIN-01 | 탐지 후 테스트 세션/계정 권한 회수 | 정해진 기한 안에 서버 거부로 전환. 브라우저 저장소 삭제만으로 완료 처리하지 않음 |
| EDGE-01 | 격리 네트워크에서 CDN/게이트웨이 경유 및 허용된 내부 직접 경로 검사 | 외부에서 origin 직접 접근이 허용되지 않거나, 서버 자체도 필수 인증·권한 통제를 적용. 실제 외부 노출 범위는 배포 설정으로 확인 |

증적에는 최소한 테스트 ID, 정책 버전, 합성 주체·객체, 예상/실제 결과, 응답 데이터 검증, 부작용/백엔드 처리 횟수, 추적 ID, 경보/회수 시간을 남깁니다. 토큰·실제 개인정보 원문은 기록하지 않습니다.

**통과는 “403/429를 한 번 봄”이 아니라** 권한 밖 데이터 반환과 부작용이 없고, 허용된 정상 요청은 작동하며, 제한·경보·회수까지 정의한 조건을 충족했다는 의미입니다. 테스트에 실패하면 해당 통제를 고친 뒤 같은 케이스와 정상 흐름을 회귀 검사합니다.

## 실행을 시작하기 위한 자료와 현재 상태

필요 자료: 테스트 API 주소와 범위, 실제 API 명세/서버 소스, 전용 A/B 및 역할별 테스트 계정의 준비 여부, 합성 데이터, 한도·폐기·경보 정책, 게이트웨이/서버/호출 제한 저장소 구성, 요청 총량/동시성/중단 기준입니다. 비밀번호·토큰을 일반 대화에 원문으로 붙일 필요는 없습니다.

현재 실제 API·테스트 계정·서버 정책은 제공되지 않았습니다. 따라서 이 문서의 시나리오 상태는 **모두 NOT_RUN(실제 서버 검증 미실행)**입니다. 이전 산출물의 로컬 참고 코드 테스트 통과를 이 항목들의 통과로 세지 않습니다. 이 문서 작성 중 추가 대상 사이트 요청도 하지 않았습니다.

권한과 다량 호출 방어를 확인하려면 다음 단계는 공개 페이지를 더 조회하는 것이 아니라 **이 정답표를 실제 서버에 연결한 통합 보안 테스트**를 수행하는 것입니다. 원본 제약에 따라 운영 부하·실제 거래·다른 사용자 데이터 접근은 피하고, 격리 환경과 합성 데이터에서 먼저 수행해야 합니다.
