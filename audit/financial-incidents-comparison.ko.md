# 최근 금융권 사고와 라이나 공개 홈페이지 위험 비교

검토 기준일: 2026-10-28 KST  
대상 범위: 기존 `www.lina.co.kr` 공개 응답·JS 증적, 금융당국 공개 발표  
관련 기술 근거: [외부 침입 가능성 검토](intrusion-review.ko.md)

## 판단

**라이나에서도 유사 사고가 발생할 가능성을 배제할 수 없습니다. 그러나 현재 자료로 동일한 침입 경로나 대규모 정보유출 가능성을 입증하지는 못했습니다.** 이 판단은 라이나에 사고가 발생했거나 다른 사고와 같은 취약 제품을 사용한다는 뜻이 아닙니다.

기존 점검에서는 브라우저의 API 오류 HTML 출력, JavaScript에서 읽을 수 있는 토큰 저장, 구버전 클라이언트 라이브러리 등을 확인했습니다. 이번에는 인증 헤더를 붙이기 전에 API의 정확한 출처를 확인하지 않는 코드 구간도 로컬 재현했습니다. 이는 조건에 따라 사용자 세션 피해로 이어질 수 있는 경로입니다.

반면 최근 금융권 사고와 같은 대규모 유출 가능성을 판단하는 데 필요한 **전체 외부 업무시스템, 서버 패치, 서버 인증·객체 권한, DB 권한, 내부 접근 범위, 탐지·대응 체계**는 확인하지 못했습니다. 홈페이지가 정상 조회되고 HTTPS가 동작한다는 사실만으로 이 항목을 통과 처리할 수 없습니다.

## F-10 — 인증 헤더 부착 전 목적지 origin 검사 공백

분류: **클라이언트의 조건부 인증정보 노출 위험. 실제 외부 전송/계정 탈취 미확인.** F-09의 XSRF 처리와는 다른, 앱 자체의 Authorization 헤더 선택 로직입니다.

### 근거

기존 `path-evidence/common/P03.js`의 문자열 offset 427부터 공통 요청 인터셉터는 다음과 같이 동작합니다.

1. 요청 URL 문자열에 `/api/` 또는 `/public/`와 같은 구간이 있는지 정규식으로 확인합니다.
2. baseURL을 설정하지만, 별도의 정확한 목적지 origin 비교 없이 위 조건에 따라 idToken을 Authorization 헤더에 넣습니다.
3. 같은 번들의 실제 Axios URL 결합 함수는 절대 URL·scheme-relative URL을 받으면 baseURL로 강제 제한하지 않고 입력 URL을 유지합니다.

따라서 해당 경로 문자열을 포함한 외부 절대 URL을 이 클라이언트에 전달하면 요청 설정에 토큰이 붙을 수 있습니다. 검토한 부분은 전체 앱 URL 입력 검증을 모두 대체하는 증거가 아니며, 상위 호출부가 URL을 고정/검증할 수도 있습니다.

### 안전한 로컬 재현

서버/API에 접속하지 않았습니다. 저장된 파일의 SHA-256을 확인한 뒤 검토한 인터셉터 구간과 Axios URL 결합 함수만 분리해 실행했습니다. 모든 호스트는 예약된 `.invalid`이며 토큰은 `AUDIT_FAKE_ID_TOKEN`입니다.

| 합성 요청 URL | 기존 코드가 결정한 목적지 | 요청 설정의 합성 Authorization |
|---|---|---|
| `/api/local-only` | 승인 API origin | 있음 |
| `/public/local-only` | 승인 API origin | 있음 |
| `https://audit.example.invalid/api/local-only` | 다른 origin | 있음 |
| `//audit.example.invalid/public/local-only` | 다른 origin | 있음 |
| `https://audit.example.invalid/local-only` | 다른 origin | 없음 |

이는 **메모리 안의 요청 설정** 결과입니다. 실제 HTTP 헤더 전송이나 브라우저 CORS/preflight는 실행하지 않았습니다. 공격자가 이 URL 인자를 제어할 수 있는 앱 진입점도 아직 확인하지 못했습니다. 따라서 토큰 유출이나 원격 침입 성공으로 보고하지 않습니다.

### 영향과 수정

공격자가 목적지 URL을 제어하는 호출부가 존재하고 브라우저 요청 조건도 충족되면 토큰이 의도하지 않은 origin에 전달될 위험이 있습니다. 고정된 정상 API 경로만 호출한다면 해당 조건이 성립하지 않을 수 있습니다.

- URL 문자열에 특정 단어가 있는지로 신뢰를 결정하지 말고, 표준 URL 파싱으로 최종 목적지의 **scheme·hostname·port를 포함한 origin**이 승인 API와 일치하는지 확인합니다.
- 이 검사는 인증 헤더를 추가하기 전에 적용하고, 검사한 URL을 실제 요청에도 사용해야 합니다. 다른 네트워크 클라이언트·업로드·재시도 경로도 동일하게 적용할지 검토합니다.
- [fixes/approved-api-url.mjs](fixes/approved-api-url.mjs)는 원본 통합 전 참고용 검사 함수입니다. HTTPS·정확한 origin만 허용하고 userinfo URL을 거부합니다. 실제 앱에는 통합하지 않았습니다.
- 목적지 검사는 서버의 인증/권한 검사나 토큰 회전, 리다이렉트 정책, XSS 방어를 대신하지 않습니다. 환경별 승인 API origin은 운영 설정에서 관리해야 합니다.
