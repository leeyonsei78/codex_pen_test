# ARTEX 엔진 포함판 사용 설명서

## 1. 이 프로그램의 목적과 현재 상태

회사에서 승인받은 환경의 취약점 후보를 찾고, 담당자가 확인·개선·재점검하는 데 사용하는 패키지입니다. ARTEX Global v0.3.15-global.1 원본 소스와 공식 Docker 이미지 실행 구성을 포함합니다.

|모드|역할|화면|
|---|---|---|
|경량 점검기|URL당 GET 1회로 보안 헤더·쿠키 속성·TLS 연결 정보를 관찰|http://127.0.0.1:8787|
|ARTEX 엔진|LLM 에이전트가 자체 도구를 실행하며 작업 목표에 따라 점검|http://127.0.0.1:8790|

두 모드는 별도의 작업·로그인·데이터를 사용합니다. 경량 점검기의 승인 체크·시간 제한·중단 버튼은 ARTEX 작업을 통제하지 않습니다. 현재 통합은 **실행 메뉴와 안내 연결**이며, 두 엔진의 작업·보고서를 하나로 합친 형태는 아닙니다. 코드와 서버 설정을 자동 수정하는 기능은 추가하지 않았습니다.

작성 환경에서는 Docker 제어 소켓의 접근 권한 오류로 ARTEX 실제 기동과 LLM 작업 실행을 검증하지 못했습니다. 설정 구문·런처 사전 검사·로컬 점검 테스트 4개를 확인한 상태입니다.

## 2. 준비

1. ZIP을 완전히 압축 해제합니다. ZIP 안에서 직접 실행하지 마세요.
2. Node.js 22 이상을 설치합니다. 현재 작업 PC에서는 v22.16.0이 확인됐습니다.
3. Docker Desktop을 켜고 Linux 컨테이너 엔진의 준비가 완료될 때까지 기다립니다.
4. 회사에서 승인한 LLM API 형식, Base URL, 모델 ID, API 키를 준비합니다. API 호출 비용과 점검 정보의 외부 전송 여부도 확인합니다.
5. 최초 실행에는 공식 ARTEX·PostgreSQL 이미지 다운로드가 필요합니다. 인터넷과 디스크 여유 공간을 확보합니다.

## 3. 회사 승인 요청

승인서에는 시스템 소유자, 담당자, 대상 URL/IP/포트와 제외 대상, 수행 시간대, 허용 기법과 금지 기법, 요청량·부하 제한, 테스트 계정, 데이터 수집·보관·삭제 기준, 중단 기준과 비상 연락 담당자를 적습니다. ARTEX는 실제 도구를 실행하는 자율 엔진이므로 경량 헤더 조회와 구분하여 승인받습니다. 먼저 소유한 격리 테스트 환경에서 동작을 확인하세요.

제출 문안 예시:

> 승인번호 [작성]에 따라 [대상]의 취약점 검증을 [기간]에 수행하고자 합니다. ARTEX의 허용 도구·기법·부하·수집 데이터와 제외 범위는 첨부 계획에 따릅니다. 이상 징후 발생 시 [담당자/연락처]와 협의해 중단합니다. 발견 결과는 담당자 검증 후 개선하고 재점검합니다.

## 4. run.bat 메뉴

|번호|기능|
|---|---|
|1|경량 웹 점검기 실행|
|2|ARTEX·PostgreSQL 시작 및 ARTEX 웹 UI 열기|
|3|ARTEX·PostgreSQL 중지. 데이터 보존|
|4|ARTEX 컨테이너 상태|
|5|초기 설정 토큰 표시. 외부 공유 금지|
|6|ARTEX 로그. 민감정보 포함 가능|
|7|API 형식·모델 ID 입력 예시 화면|
|8|전체 사용 설명서 화면|

## 5. ARTEX 처음 실행하기

1. `run.bat` → **2번**. 다운로드와 기동이 끝날 때까지 기다립니다.
2. 브라우저에서 http://127.0.0.1:8790/setup 에 접속합니다.
3. `run.bat` → **5번**에서 확인한 토큰을 설정 토큰 칸에 입력합니다.
4. 본인이 정한 고유 관리자 비밀번호를 입력합니다. 최소 8자이며 긴 비밀번호를 사용하세요.
5. 사용자명 **ARTEX**와 만든 비밀번호로 로그인합니다.
6. 시스템 → LLM에서 공급자 형식, 모델 ID, Base URL, 실제 API 키를 입력하고 **연결 테스트** 후 저장합니다. 메뉴 **7번**에 형식별 예시와 공식 확인 링크가 있습니다.
7. 표시 언어를 한국어로 선택합니다.

토큰은 최초 관리자 설정용이고, 관리자 비밀번호는 로그인용이며, API 키는 LLM 인증용입니다. 서로 대체할 수 없습니다. 비밀번호·토큰·API 키를 채팅이나 보고서에 붙이지 마세요.

## 6. 승인 후 점검하고 개선하기

1. ARTEX 작업 화면에서 승인 대상과 목표·제외 범위를 명시합니다. 승인 내용을 입력했다고 네트워크 수준에서 범위가 자동 강제된다고 가정하지 마세요.
2. 계획과 도구 승인 설정을 검토하고 소유한 테스트 환경에서 시작합니다. 작업 중 활동과 대상 서비스 상태를 관찰합니다.
3. 이상 징후가 발생하면 ARTEX 자체 작업 제어로 중단하고, 필요하면 메뉴 **3번**으로 전체 엔진을 중지합니다.
4. 발견 항목은 **취약점 후보**입니다. 요청·응답·재현 조건·영향·오탐 여부를 담당자가 확인합니다.
5. 담당 개발·운영팀이 코드 또는 설정을 수정합니다. 운영 반영은 회사 변경관리 절차에 따릅니다.
6. 같은 재현 조건으로 재점검하고, 수정 전후 증거와 잔여 위험을 기록합니다. 자동 결과만으로 조치 완료를 판정하지 않습니다.

목표 입력 예시:

> 승인번호 SEC-2026-0123. 소유한 격리 테스트 앱 [실제 URL]만 점검한다. 수행 기간·허용 기법·제외 범위·부하 한도는 승인서를 따른다. 발견 항목별 재현 조건과 개선 권고를 기록한다.

컨테이너의 127.0.0.1은 Windows PC가 아닙니다. PC에서 실행 중인 소유 테스트 앱에는 예를 들어 `http://host.docker.internal:3000`을 사용할 수 있습니다. 앱 실행 여부·포트·승인 범위를 먼저 확인하세요. 이 주소는 실제 테스트 앱을 자동 설치하지 않습니다.

## 7. 경량 점검기 사용하기

메뉴 **1번** → 프로젝트·승인번호·수행자·기간·허용 origin·URL 입력 → 계획 검토 → 회사 승인 확인 → 계획 재검토 → 실행. 설정 변경 후에는 계획을 다시 검토합니다. 완료 후 화면에서 JSON을 다운로드하거나 `reports/`를 확인합니다. 이 모드의 결과는 헤더와 쿠키 등의 설정 관찰이며 전체 취약점 검사가 아닙니다.

## 8. 종료·데이터 관리

ARTEX는 창이나 브라우저를 닫아도 동작할 수 있습니다. 메뉴 **3번**으로 중지하세요. 경량 서버는 해당 창에서 Ctrl+C로 종료합니다. 두 모드의 종료 방법이 다릅니다.

`engine-runtime/.env`에는 DB 비밀번호와 토큰, `engine-runtime/data/`에는 엔진 파일이 저장됩니다. PostgreSQL 데이터는 Docker 볼륨 `artex-review-engine_engine_pgdata`에 보관됩니다. 메뉴 3은 데이터를 삭제하지 않습니다. 백업·접근 권한·삭제는 회사 정책에 따르세요. 실제 키·보고서·런타임 폴더가 들어간 ZIP을 다른 사람에게 배포하지 마세요.

## 9. 오류 확인

|현상|확인 방법|
|---|---|
|Docker is not ready|Docker Desktop 실행 및 Linux containers 모드 확인|
|Access is denied / Permission denied|Docker Desktop이 켜져 있어도 현재 실행 계정·관리형 환경의 Docker 소켓 권한이 거부될 수 있음. 본인 계정의 터미널에서 실행해 보고 회사 IT에 사용자별 Docker 접근 권한 확인 요청|
|이미지 다운로드 실패|사내 프록시·레지스트리 접근 정책 확인|
|8790 연결 실패|메뉴 4의 상태와 메뉴 6의 로그 확인. 포트 충돌 확인|
|초기 토큰 불일치|다른 압축 해제 폴더가 아닌 실제 실행 폴더에서 메뉴 5 확인|
|LLM 연결 실패|API 형식·Base URL·모델 ID·키 권한·사용량·VPN 정책 확인|

PowerShell에서 실행 폴더로 이동한 후 다음 읽기 전용 명령으로 진단할 수 있습니다.

```powershell
node --version
docker version
docker compose version
node engine-control.mjs check
```

Docker의 Server 항목이 나오지 않거나 접근 거부가 있으면 컨테이너 기동 단계로 넘어갈 수 없습니다. 소켓 접근 제한을 임의로 풀거나 엔진을 인증 없이 외부에 공개하지 마세요.
